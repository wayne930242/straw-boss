## Context

See `proposal.md` - Why for the motivating gap and the two facts that shaped this design (SendMessage's actual delivery contract vs. herdr `agent prompt`'s; a plan task's status-file write being bookkeeping, not notification, confirmed live during this change's own investigation when a plan task's `done` status file sat unconfirmed as ever having been noticed).

Current mechanics this design builds on, all unchanged in their own right:
- `SendMessage`'s own contract: a message to a live, correctly-addressed peer enqueues and drains at that peer's next tool round; if the receiving session's permission-mode class doesn't accept cross-session input automatically (`crossSessionInbound` unset), it is held pending manual review — never silently dropped either way.
- `notifying-main-agent`'s existing addressing fix: the main agent runs `/rename straw-boss-orchestrator` once per session (`cross-session-coordination.md`) so a dispatched agent's `SendMessage` has a deterministic, correct target — this design depends on that step already having run; it does not change it.
- Plan tasks' existing `report-task-status.py` write + `Monitor`-polling-loop pattern (`plan-mechanics.md`) — kept, but reframed as the bookkeeping half of the contract, not the notification half.
- Standalone dispatches' existing active-detection pattern, currently only written down in `init`'s Task 9 (`herdr agent wait --until idle --until blocked` + `agent read`, or `claude-p` process/background-notification) — kept as the fallback, generalized to every specialist skill instead of living only in `init`.

## Goals / Non-Goals

**Goals:**
- Every dispatched agent (plan or standalone) has one defined, guaranteed-delivery way to tell its main agent it reached `done`/`failed`/a checkpoint.
- The main agent's own active-detection mechanics stop being the primary way it learns of an outcome and become a bounded fallback for a dispatch that's gone quiet.
- The fix generalizes cleanly to every specialist skill that dispatches (`shipping-task`, `inspecting-app`, `investigating-app`, `troubleshooting-app`, `init`, `create-great-harness`), from one canonical description (`cross-session-coordination.md` + `notifying-main-agent`), not six separate restatements.
- A dispatched agent's main-agent reachability is available as a structured, script-readable fact, not only a value stated once in its own prompt's prose.
- A dispatched agent can make its own progress visible at any point, not only at a terminal state, so a peek can usually be answered without joining its live pane.
- A standalone dispatch has the same terminal-state durability a plan task already has, using the same generalized script rather than a second one-off mechanism.

**Non-Goals:**
- Not changing `claude-p`'s own completion signal (process exit / background-task notification) — it already reliably signals its own process boundary; this design adds a `SendMessage` push before it exits as the primary notice, but does not touch how the harness itself reports the process ending.
- Not defining a numeric "fallback threshold" constant here — see Decisions below for why this stays behavioral (tied to existing triggers) rather than a hardcoded timeout.
- Not touching the push/merge authorization flow (`awaiting-authorization`) — confirmed with the user as correct as-is.
- Not having a script perform the `SendMessage` send itself — `SendMessage` is a Claude Code agent tool call, not a shell-invocable primitive, so no script in this design can issue it on the dispatched agent's behalf. Scripts in this design only ever do two things: read/write files, and print back what the agent needs in order to make the tool call itself.

## Decisions

**`SendMessage` is required for the report branch; herdr `agent prompt` is optional and additive, never a substitute.** This is a deliberate asymmetry with the existing question branch (herdr primary, `SendMessage` fallback), not an oversight. The question branch's ordering exists because a lost *question* just means the dispatched agent tries something else or falls back to asking the user — low cost either way. A lost *completion report* means the main agent silently sits on a finished task, which is the exact failure this change exists to close — so the report branch requires the one channel whose delivery is actually guaranteed once addressing is correct.

**Plan tasks push too, rather than leaving them "already solved."** Alternative considered: leave plan tasks alone since `Monitor` already watches their status file, and scope this whole change to standalone dispatches only (the original framing). Rejected because the live incident during this change's own investigation showed the exact failure mode `Monitor` coverage is supposed to prevent — a `done` status file with no confirmation the watching main agent's `Monitor` loop was still alive to see it. `Monitor` remains the mechanism for wave-scheduling reads (`read-plan-status.py --ready`/`--in-flight`), which genuinely needs the status file as data; it stops being relied on as the *notification* half.

**No new numeric fallback-threshold constant.** Alternative considered: a fixed idle-timeout (e.g. reuse `init`'s existing `--timeout 120000` verbatim) as "the" threshold before the main agent falls back to active detection. Rejected as a global constant — a quick audit and a multi-hour development task have very different reasonable quiet periods, and this project already has a fitting, existing trigger set instead of a fixed clock: `peeking-work`'s role as the canonical live-check ("Idle in-flight tasks — peek, don't just trust the note" already exists in `boss-say`'s plan-batch loop), the main agent's own turn ending with a dispatch still open, and an explicit user status question. The fallback fires on those triggers rather than a standalone timer; where an existing skill already runs a bounded wait (e.g. `init`'s `--timeout 120000` for a bootstrap dispatch, or `dispatch-mechanics.md`'s `--wait --timeout 120000` for initial submission confirmation), that wait is unchanged — this design does not touch it, since it's confirming delivery of the *initial task*, not later completion.

**Push message shape reuses `notifying-main-agent` Task 2's existing self-identification convention**, with a status-marker prefix (e.g. `[from agent <name>] STATUS: done — <one-line summary>` / `STATUS: failed — <reason>` / `STATUS: checkpoint:<name> — <what it's ready to do>`) so the two branches (question vs. report) stay visually distinguishable in the same channel without needing a separate protocol or tool.

**`notify_when_idle` (a `SendMessage` option letting the main agent subscribe to a same-machine session's next idle/exit event) was considered as an alternative or complement** — it would let the main agent get notified without the dispatched agent needing to remember to push anything. Not adopted as part of this change: it only covers same-machine `herdr-pane` sessions (not `claude-p`, not a plan task's own status-file-driven wave logic), and the user's decision was specifically that the dispatched agent's own push is the mechanism. Left as a possible future enhancement, not a requirement here.

**Main-agent reachability moves from prompt-only prose to a structured field on the instruction file, read back by a new script (`get-main-agent.py`).** Alternative considered: leave it as prose only (status quo) and trust the dispatched agent's own recall. Rejected: a long-running or `/compact`-ed task's context may no longer reliably retain a value stated once, early, in its own prompt — the whole point of this change is a *reliable* push, so its target must be at least as reliable as the send itself. Concretely: `dispatch-task.py write` gains an optional `--main-agent-pane-id` (`herdr-pane` only; the caller already resolves `$HERDR_PANE_ID` before assembling the prompt's prose, so this is the same value, just also recorded structurally) and always records the fixed `SendMessage` peer-name convention (`straw-boss-orchestrator`) as an explicit `main_agent_send_message_peer` field, so the reader never has to already know the convention. `get-main-agent.py --instruction-path <path>` prints both fields back. The dispatch prompt still states the reachability info in prose too, for a human skimming it and so nothing about the existing flow regresses — the script read is the authoritative source at report time; the prose is a redundant restatement, not the other way around. This does not fully close the separate "was `/rename` run before this instruction was written" risk (see Risks) — it just means there is one consistent source of truth instead of two independently-drifting ones (prose vs. a field).

**Progress logging is a separate, append-only file per dispatch, never the same file a `Monitor` loop dedups by filename.** Alternative considered: reuse a plan task's existing single-object status file for intermediate updates too (write `{"status": "progress", "note": ...}` there between terminal writes). Rejected: `plan-mechanics.md`'s `Monitor` loop already dedups strictly by filename, emitting only on a file's first appearance (documented today for the `cancelled`-overwrites-`awaiting-*` case) — an intermediate write to that same filename would get treated as "already seen," and a *later* genuine terminal write to the same filename would then never be re-emitted, silently breaking wave detection. `report-progress.py --instruction-path <path> --note "<text>"` instead appends to a sibling `<instruction-path stem>.progress.jsonl` — one line per call, any number of calls, never overwritten, and never the file any `Monitor` loop watches. `peeking-work` is updated to read this file's tail as its first move.

**Standalone dispatches get a real terminal-state file, by generalizing `report-task-status.py` rather than writing a second script.** Alternative considered: leave standalone dispatches with only the `SendMessage` push and no durable record, matching the original (narrower) framing of this change. Rejected once progress logging and reachability lookup both already needed a script keyed on `--instruction-path`: not giving standalone dispatches the same terminal-state durability plan tasks have would leave the fallback pull path (Requirement: "Active detection is a bounded fallback") with nothing better to read for a standalone dispatch than a live pane transcript, undercutting the whole point of adding a fallback. `report-task-status.py` gains `--instruction-path <path>` as an alternative to `--plan`/`--task`: given an instruction path, it reads that file — if it carries `plan_id`/`task_id`, it writes to the existing `~/.straw-boss/plans/<slug>/status/<task_id>.json` location (unchanged location, so `Monitor`/`read-plan-status.py` need no changes); otherwise it writes to a sibling `<instruction-path stem>.status.json`. Every dispatch — plan or standalone — already has an instruction path (`dispatch-task.py write` always produces one), so a dispatched agent never needs to know or care which case it's in; it always calls the same script the same way.

## Risks / Trade-offs

- **A `SendMessage` push guarantees enqueue-and-drain at the main agent's next tool round, not that the main agent's own session is still running at all.** If the main agent's session has ended entirely, no mechanism in this design (push or pull) recovers that — there is no one left to notify. → Mitigation: out of scope; if the orchestrating session is gone, the user's own status check (`dispatching-work`'s List branch, `peeking-work`) is how they discover an orphaned dispatch, unchanged by this design.
- **A dispatched agent cannot itself verify its push was seen** (confirmed by the live incident this design is grounded in — the agent could confirm its own file write, not the orchestrator's awareness of it) — a future misreading of this design could have the agent retry or escalate based on an assumed non-delivery it can't actually detect. → Mitigation: `dispatch-completion-reporting`'s requirements place verification responsibility on the main agent (via the fallback), never on the dispatched agent; the dispatched agent's job ends at sending the push once.
- **Reversing two existing Red Flags (`init`, `create-great-harness`) changes established, previously-deliberate guidance** — a reader of just one of those two files, not this change, could reinstate the old "never push" rule from memory. → Mitigation: both files' Red Flags sections are rewritten in place (not left stale beside a contradicting instruction elsewhere), and both now point at `cross-session-coordination.md`/`notifying-main-agent` as the single source, consistent with how the rest of the plugin avoids restating shared mechanics.
- **Requiring `SendMessage` specifically (not just herdr) for the report assumes `/rename straw-boss-orchestrator` already ran this session** — if a dispatch instruction is assembled before that step (a sequencing bug elsewhere, not something this design introduces), the push would misaddress. → Mitigation: unchanged pre-existing requirement (`dispatching-work` Task 1 already requires this before the first `herdr-pane` dispatch); this design doesn't relax or duplicate that check.

## Migration Plan

Mostly documentation/prompt, plus four small, additive script changes — no runtime data migration for anything already written (existing instruction files simply lack the two new fields until rewritten by a future dispatch; nothing reads them as required on an old file). Sequencing within `tasks.md`: scripts first (`dispatch-task.py`'s new fields, `get-main-agent.py`, `report-progress.py`, `report-task-status.py`'s `--instruction-path` generalization, and `dispatch-mechanics.md`'s schema doc, since every doc change below refers to them), then the shared coordination docs (`notifying-main-agent`, `cross-session-coordination.md`, `plan-mechanics.md`), then the specialist skills and `dispatching-work`'s own table/Red-Flags, then `peeking-work` (reads the new progress log), then `init`/`create-great-harness` last (since their existing Red Flags are what this change reverses, they should point at the now-updated shared sources rather than being edited in isolation), then `docs/architecture.md`/`docs/roles.md` for consistency. No rollback mechanics beyond reverting the commit — nothing this change writes is stateful in a way that resists rollback.
