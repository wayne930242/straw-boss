## Why

A dispatched agent has no reliable way to make sure its main agent actually notices it reached `done`, `failed`, or a checkpoint the main agent must act on (e.g. ready to push/merge). This was first raised for a **standalone** (non-plan) dispatch — `shipping-task`, `inspecting-app`, `investigating-app`, `troubleshooting-app`, and `init`'s/`create-great-harness`'s bootstrap dispatches have no status file and no defined completion signal at all; `skills/init/SKILL.md` Task 9 and `skills/create-great-harness/SKILL.md` Task 6 are the only two skills with a defined mechanism (active polling: `herdr agent wait`/`agent read`, or `claude-p` process exit), and both explicitly forbid pushing a completion report through `notifying-main-agent`, reasoning the channel is "fire-and-forget with no delivery guarantee."

Investigating that reasoning surfaced two distinct facts that change the shape of the fix:

1. **`notifying-main-agent`'s two channels do not share one reliability class.** `SendMessage` is a harness-level mailbox: a message to a live, correctly-addressed peer enqueues and is guaranteed to drain at that peer's next tool round (confirmed from the tool's own contract) — worst case, if the receiving session's permission-mode class doesn't accept cross-session input automatically, the message is held pending manual review, never silently dropped. `herdr agent prompt` (typing into a pane) has no such guarantee — it is genuinely fire-and-forget, and this project's own docs already record a first-run interruption swallowing a submitted prompt while the command still reported success. The original "never push a report" rule was reacting to `herdr agent prompt`'s unreliability but applied it to the whole channel, including `SendMessage`, which doesn't share the same failure mode once the main agent is correctly addressed (`cross-session-coordination.md`'s `/rename` step already exists to fix mis-addressing).
2. **A plan task's status-file write is not itself a notification, and this is not hypothetical.** Live during this change's own investigation, a plan task wrote its status file (`done`, with a real timestamp and note) and the dispatched agent itself flagged — correctly — that a successful file write proves nothing about whether the orchestrating main agent's own `Monitor` loop was still running to notice it. Plan tasks already looked "solved" because `Monitor` watches the status directory, but that coverage only exists while a `Monitor` is actually alive and watching; the status file is bookkeeping (what `plan.json` sync and wave computation read), not proof anyone was told.

Given both facts, the fix is the same for plan and standalone dispatches: a dispatched agent pushes a `SendMessage` notification the moment it reaches `done`/`failed`/a checkpoint, in addition to whatever state it already persists (a plan task keeps writing its status file — wave computation still needs it); the existing pull mechanics (`Monitor` for plan tasks; `herdr agent wait`/`agent read` or process exit for standalone) become a fallback used when the main agent hasn't heard from a still-open dispatch in too long, not the primary way it finds out.

Separately, the same coordination surface has a second, smaller gap: a dispatched agent stuck on genuine technical difficulty (not missing context — that's already `notifying-main-agent`'s informational case — and not a values/architecture call that's inherently the user's) has no step between those two before landing on `awaiting-user-input`. The user asked for a stronger-second-opinion step (e.g. this session's own `advisor` tool, when available) to be tried first.

## What Changes

- `notifying-main-agent` gains a second, distinct branch — reporting the dispatched agent's own `done`/`failed`/checkpoint state to its main agent — alongside its existing informational-question branch. Unlike the question branch (herdr primary, `SendMessage` fallback), the report branch requires `SendMessage` specifically — that's the send whose delivery is actually guaranteed; a herdr `agent prompt` to the main agent's own pane may still be sent alongside it as a faster visible nudge where reachable, but never as a substitute for the `SendMessage` send.
- **BREAKING**: `skills/init/SKILL.md` Task 9 and `skills/create-great-harness/SKILL.md` Task 6 (and their matching Red Flags) currently state, as a hard rule, that a completion report must never be pushed through `notifying-main-agent`. This rule is reversed: the `SendMessage` push becomes the primary signal; the existing pull mechanics become a fallback for when the main agent hasn't heard from a still-open dispatch in too long, not the sole mechanism.
- **Plan tasks also push.** A plan task's dispatch instruction keeps telling it to write its status file (`report-task-status.py` — unchanged, still what `plan.json` sync and wave computation read), and additionally tells it to send the same `SendMessage` push standalone dispatches send. `Monitor`-watching the status directory remains the wave-scheduling mechanism; it is no longer relied on as the sole notice that a task finished.
- Every dispatch instruction (plan or standalone) states the reporting obligation alongside the main-agent reachability info it already states for informational questions — closing a gap in `inspecting-app`/`investigating-app`, which currently state no `notifying-main-agent` pointer at all.
- `dispatching-work`'s "Three checkpoint types" table and `references/cross-session-coordination.md`'s "What the dispatch instruction states, per mode" block (the single source both `shipping-task` and the other specialist skills point at) are updated to describe the push-primary/pull-fallback contract.
- A dispatched agent stuck on genuine technical difficulty (not context it can get informationally from its main agent, not a judgment call reserved for the user) tries a stronger second opinion first, if one is available to it, before escalating to `awaiting-user-input` — worded permissively (no specific tool hardcoded), since a dispatched agent in another app or under another agent kind may not have the same tools this session does. The existing `awaiting-authorization` flow (push/merge, relayed through the main agent to the user) is unchanged.
- **Main-agent reachability becomes a structured, script-readable field, not only prose.** `dispatch-task.py write` records the main agent's herdr pane id (`herdr-pane` mode) and its fixed `SendMessage` peer name on the instruction file itself; a new script, `get-main-agent.py`, lets a dispatched agent read this back directly at report time — the authoritative source, not a value it has to recall correctly from prose stated once in its own dispatch prompt (which a long or `/compact`-ed task's context may no longer reliably retain).
- **A dispatched agent can log progress at any point, not only at a terminal state or checkpoint.** A new script, `report-progress.py`, lets it append a timestamped, free-text note at any stage of its work — no `SendMessage` push involved, just a durable trail. `peeking-work` reads this trail as its primary source, falling back to a live pane/transcript read only when the trail doesn't answer the question, so the main agent (or the user, via `peeking-work`) can usually tell what a dispatched agent is doing without joining its actual work pane.
- **Standalone dispatches get terminal-state parity with plan tasks.** `report-task-status.py` is generalized to accept a dispatch instruction directly (`--instruction-path`), not only a plan task (`--plan`/`--task`), so a standalone dispatch also has a real recorded terminal state to fall back on — not just the `SendMessage` push and a live pane read.

## Capabilities

### New Capabilities
- `dispatch-completion-reporting`: defines how a dispatched agent — plan or standalone — notifies its main agent it reached `done`, `failed`, or a checkpoint the main agent must act on: a `SendMessage` push as the guaranteed-delivery primary signal, any existing state-persistence mechanism (a plan task's status file, or a standalone dispatch's new equivalent) as bookkeeping rather than notification, script-readable main-agent reachability instead of prose recall, an any-time progress log so a peek doesn't require joining the live pane, and the main agent's active pull as a fallback bounded by how long the dispatch has gone quiet without a push.
- `dispatched-agent-escalation`: defines the order a dispatched agent follows when it cannot resolve something on its own — informational question to its main agent (context it already has), then a stronger second opinion if one is available (genuine technical difficulty), then `awaiting-user-input` (a judgment call reserved for the user) — distinct from, and never substituting for, the unchanged `awaiting-authorization` gate on push/merge.

### Modified Capabilities
- `dispatch-authority`: "Dispatched-agent failure reporting is unaffected" currently states a failed dispatched agent reports "through its status file as before" — both because a standalone dispatch has no status file at all, and because a plan task's status file is no longer the notification mechanism (it's bookkeeping; the `SendMessage` push is). The requirement's mechanism clause is corrected accordingly, without changing its actual guarantee (the main agent still asks the user before redispatching a failure).
