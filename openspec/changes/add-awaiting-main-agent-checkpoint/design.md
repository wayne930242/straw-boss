## Context

See `proposal.md` - Why for motivation. Relevant current state:

- `scripts/report-task-status.py`'s `VALID_STATUSES = ("done", "failed", "awaiting-authorization", "awaiting-user-input", "cancelled")` is the only enum gate on checkpoint values; both the plan-task status file (`~/.straw-boss/plans/<slug>/status/<task_id>.json`) and the standalone status file (`<app>--<slug>.status.json`) are plain JSON, fully overwritten on each write (`path.write_text(json.dumps(payload...))`), never merged.
- `scripts/wrap-up-task.py`'s terminal-status guard is a membership test (`status not in ("done", "failed", "cancelled")`), not an enumerated list of non-terminal values — a new non-terminal status is refused automatically with zero code change, only its two hardcoded error-message strings mention "awaiting authorization or user input" by name.
- `scripts/get-main-agent.py` is the existing worker→main-agent reachability lookup: pure JSON read, no side effects, no subprocess. It exists because the *dispatched agent* needs to resolve its main agent's reachability from its own instruction file.
- At the time of this checkpoint change, herdr calls were agent-issued and scripts were state-only. The later herdr-primary reporting refinement deliberately added a second orchestration script exception: `report-task-status.py` writes status before shelling out to `herdr agent prompt`.
- `claude-p` has no resumable live pane, so a task that hits an unresolvable blocker reports `failed`; herdr-pane workers pause live, while headless Codex checkpoints can be continued later with `codex exec resume`.
- `dispatch-mechanics.md`'s herdr-pane dispatch step 6.5 already established the pattern for confirming a `herdr agent prompt` actually landed (read the pane's transcript back, don't trust the CLI's success return alone) after a documented live failure where a first-run interruption swallowed a submitted prompt while the CLI still reported success.

## Goals / Non-Goals

**Goals:**
- Give a dispatched agent blocked on the main agent's own judgment/authority a first-class, trackable checkpoint, reusing the durable status-file machinery rather than inventing a parallel one.
- Make "the main agent replied" and "the checkpoint is no longer silently stale" the same provable event, not two steps the main agent can complete only one of.
- Leave every file's existing schema untouched — purely additive. (One correction made along the way, not a behavior change: `notifying-main-agent`'s own instructions claimed a non-`done`/`failed` checkpoint has no status-file write, contradicting `plan-mechanics.md`'s own "Authorization checkpoints"/"User-clarification checkpoints" and `report-task-status.py`'s `VALID_STATUSES`, which already write `awaiting-authorization`/`awaiting-user-input` today. Fixed as part of this change since the new checkpoint sits right next to that wrong claim.)

**Non-Goals:**
- No worker-side bounded reminder/retry while blocked.
- No support for pausing and resuming a `claude-p` process; it continues to report `failed` with the situation in `--note`.
- No attempt to make a provider-specific fast channel authoritative; durable status remains the scheduling source of truth.

## Decisions

### The new status reuses the existing status-file shape; no new file format
`awaiting-main-agent` is added to `VALID_STATUSES` and otherwise flows through the exact machinery `awaiting-user-input` already does (same file, same writer, same content-revision watcher, same `wrap-up-task.py` refusal-by-membership check).
**Alternative considered:** encode "who answers" as a note-level convention inside the existing `awaiting-user-input` status (e.g. a `--note` prefix). Rejected — it's not machine-checkable, so the watcher and `wrap-up-task.py` can't distinguish the two without parsing free text, defeating the point of making this a first-class state.

### The reply is delivered by resuming the worker's own pane, not by a new SendMessage
The main agent's reply is sent with `herdr agent prompt` into the worker's existing pane — the same resume mechanism `dispatch-authority`'s existing "Redirect a dispatched agent mid-task" requirement already uses, and the same way a human answers `awaiting-user-input` today (directly in the pane, not via a queued message).
**Why not `SendMessage`:** the reply targets the recorded live pane directly, works for both providers, and resumes the exact waiting task. `SendMessage` is a Claude-to-Claude-only fallback and is not the cross-provider reply seam.

### `reply-to-worker.py` performs the send itself — a deliberate, scoped exception to "scripts are pure state"
This change originally made `reply-to-worker.py` the first deliberate script exception to state-only I/O: it shells out to herdr and confirms delivery before recording resolution. The later reporting refinement applies the same locality principle to `report-task-status.py`, but with the inverse ordering required for recovery: write durable status first, then prompt the main-agent pane.

**`agent read` has no JSON output mode at all — confirmed live, and this shipped broken until it was.** `herdr agent get`/`agent prompt` return JSON by default; `agent read`'s only output options are `--format text|ansi` (default text) — its stdout is a raw rendering of the pane, not a structured payload. An earlier version of this script called the same JSON-parsing helper for all three subcommands, which meant `agent read` would raise a `JSONDecodeError` on every single real invocation — confirmed live against a throwaway test pane before task 5.1b was closed out. Fixed by giving `agent read` its own raw-stdout path (`run_herdr_raw`), separate from the JSON-parsing one (`run_herdr`) `agent get`/`agent prompt` still use — `.result.agent.name` for the former is also now confirmed live, not just inferred.

**Retry is gated on a genuine herdr failure, not a confirmed-but-empty read.** With `agent read` no longer JSON, there's no schema to mismatch — a raised error from it is a real CLI failure (timeout, pane gone) and never triggers a resend; only a full poll window (below) that completes without ever finding the reply retries.

**No `--wait` on the send; confirmation is a short poll, not a single instant read.** `herdr agent prompt --wait` blocks until the *whole turn* ends, not until the message is delivered — but the worker's pane is resumed specifically so it can do real work (redispatch a dependency, resolve a conflict), which can easily run past any prompt-submission timeout. `--wait` would then fail a send that actually succeeded, and the caller would retry into an already-working pane. Dropping `--wait` avoids that, but flips the risk the other way: read the transcript once, immediately, and the reply may not have registered yet, triggering a spurious resend. Fixed by polling `herdr agent read` a bounded number of times (`CONFIRM_POLL_ATTEMPTS` × `CONFIRM_POLL_INTERVAL_S`, a few seconds each) before concluding "not landed" — short enough to never approach how long the worker's subsequent work might take, long enough to absorb ordinary transcript-sync latency. Confirmation also dropped the "must have content following the reply" requirement (originally borrowed from `dispatch-mechanics.md` step 6.5's fresh-pane dispatch case) down to "the reply text is present at all" — requiring visible worker output afterward is exactly the same timing trap as `--wait`, just moved into the confirmation check instead of the send.
**Why:** the bug being fixed is specifically "the main agent decided the answer only in its own reasoning and never executed the send." The only way to make delivery and record-keeping a single provable event is for one process to own both steps — splitting them across a script call and a separate manual `herdr agent prompt` reintroduces the exact same class of bug (forgetting the second step) that this feature exists to eliminate.
**Alternative considered:** keep scripts I/O-only; have `reply-to-worker.py` just resolve reachability (mirroring `get-main-agent.py`'s shape) and require the main agent to separately run `herdr agent prompt` itself, then call a second script to clear the checkpoint. Rejected — two independently-forgettable steps instead of one, no improvement over today.
**Alternative considered:** always fall back to `SendMessage` if `herdr agent prompt` fails. Rejected — this checkpoint is herdr-pane-only by construction (see Non-Goals); a worker that could reach this state always has a `herdr_pane_id` to resume through, and papering over a failed delivery with a differently-addressed message hides the real problem (pane closed, agent crashed) instead of surfacing it.

### Confirmation matching is whitespace-normalized — confirmed live to matter, not a hypothetical
`reply_landed` collapses all whitespace runs to a single space in both the transcript and the reply before searching, instead of an exact substring match. Confirmed live against a real herdr pane: a long reply that hard-wraps at the pane's column width turns the space before the wrap point into a newline, so an exact match against the original text fails even though the reply landed — the script then retried, and the worker genuinely executed the same reply a second time (the exact non-idempotent double-send this whole feature exists to prevent, reproduced live during task 5.1b before this fix). `CONFIRM_READ_LINES=500` was separately confirmed live: the original prompt was still findable in a 500-line read after 80 lines of the worker's own subsequent output, but not in the original 40-line window — validating the round-3 advisor fix against real pane behavior, not just a mock.

### Resolution is recorded as additive fields on the existing status file, not a new status value
On confirmed delivery, `reply-to-worker.py` adds `resolved_by_main_agent_at` (timestamp) and `main_agent_reply` (the text sent) to the *same* status JSON, leaving `status: "awaiting-main-agent"` unchanged. This lets the watcher and a human distinguish "already replied, worker hasn't resumed yet" from "never replied to" without adding a new enum value or touching `report-task-status.py`'s writer contract. These fields are naturally superseded the next time the worker itself writes a terminal status.

### `wrap-up-task.py` needs no logic change, only its error-message text
Confirmed by reading the script: the terminal-status guard is `status not in ("done", "failed", "cancelled")`, a membership test — `awaiting-main-agent` is refused automatically. Only the two hardcoded strings ("...still awaiting authorization or user input") should be updated to also name the new checkpoint, for accuracy — cosmetic, no behavior change.

### Every instruction-assembling skill must state the checkpoint exists, not just the reference doc that defines it
A worker only knows `awaiting-main-agent` is available if its own dispatch instruction text says so — the skill docs describing the mechanics live in the plugin, not in what a given worker was actually told for its dispatch. `plan-mechanics.md`'s existing item list (what a plan-task instruction must state) already had this exact pattern for `awaiting-user-input`; `shipping-task` (which assembles a *standalone* dispatch's instruction, a separate skill from plan-task assembly) had it too, for the same checkpoint. Both needed the parallel addition for `awaiting-main-agent`, or the checkpoint would exist in the state machine with no path for a worker to ever actually enter it. `boss-say` (which drives a dispatched batch's tick loop) and `docs/roles.md` (the authority framework `dispatch-authority`'s spec delta references) needed corresponding updates for the same reason — anywhere the two existing checkpoints were enumerated by name, the third had to join them or the enumeration became misleading rather than merely incomplete.

## Risks / Trade-offs

- **[Risk] orchestration scripts shelling out to `herdr` break the former scripts-are-pure-state convention** → Mitigation: scoped to the two deep seams that must make state and delivery one operation: confirmed reply delivery in `reply-to-worker.py`, and status-before-notify in `report-task-status.py`.
- **[Risk] Worker's pane closed or crashed since sending its push** → Mitigation: the liveness check (mirroring `asking-peer-agents`) fails loudly before any send is attempted; the status file is left untouched (still openly `awaiting-main-agent`, not falsely marked resolved), and the script exits non-zero so the main agent surfaces this to the user rather than silently losing the checkpoint.
- **[Risk] `herdr agent prompt` reports success but the prompt didn't actually land** (the documented first-run-interruption failure mode) → Mitigation: poll-based transcript confirmation + one retry, gated on a poll window that genuinely never finds the reply (see the no-`--wait`/polling decision above) rather than on any failure to read — a genuine herdr CLI failure never triggers a second send against a live pane.
- **[Risk] `--wait` would fail a send that actually succeeded, once the resumed worker's own work runs long** → Mitigation: dropped `--wait` entirely; confirmation is a bounded poll on the transcript instead of blocking on the whole turn.
- **[Trade-off] Confirmation checks only that the reply text reached the transcript, not that the worker has acted on it** → Accepted; requiring visible worker output afterward reintroduces the same timing trap `--wait` had, and distinguishing "received" from "acted on" isn't this script's job.
- **[Risk — confirmed live, fixed] Presence-only confirmation against a *fixed-size* tail read has the same failure shape as `--wait`, just relocated** → A busy worker's own output scrolls the reply line out of a narrow window within the poll interval, so the *more* successfully the reply landed, the more likely confirmation fails and triggers a resend. Confirmed live during task 5.1b: the original prompt was findable in a 500-line read after 80 lines of new output, but not in a 40-line one. Mitigation: `CONFIRM_READ_LINES` set to 500.
- **[Risk — confirmed live, fixed] `herdr agent read` returns no JSON at all** (only `--format text|ansi`) → An earlier version parsed it as JSON like `agent get`/`agent prompt`, which raised on every real invocation. Confirmed and fixed during task 5.1b: `agent read` gets its own raw-stdout path; `agent get`'s `.result.agent.name` is now confirmed live, not inferred.
- **[Risk — confirmed live, fixed] Line-wrapped replies broke exact substring matching, causing a real duplicate send** → A long reply hard-wraps at the pane's column width; the space at the wrap point becomes a newline, so `transcript.rfind(reply)` misses it even though it landed. Confirmed live during task 5.1b: this triggered the script's own retry, and the worker executed the same reply twice. Mitigation: whitespace-normalized comparison (collapse all whitespace runs to one space on both sides before matching).
- **[Trade-off] This checkpoint remains unavailable to `claude-p` workers** → Accepted, unchanged from the existing `awaiting-user-input`/`awaiting-authorization` limitation; not a new gap introduced here.
- **[Resolved follow-up] Per-filename dedup could miss a checkpoint's later terminal rewrite** → `watch-plan-status.py` now deduplicates by full content revision and retries malformed partial writes, so every valid rewrite emits and a restarted watcher recovers current state.

## Migration Plan

Purely additive — no schema migration for existing in-flight dispatches. An in-progress task never reaches `awaiting-main-agent` unless a dispatch instruction explicitly directs it to (per the updated `notifying-main-agent` guidance), so nothing currently running is affected. Rollout is landing the changed files (scripts, skill docs, spec deltas) with no data transformation step. Rollback is a plain revert — no other status's behavior, file shape, or script contract changes, so reverting this change cannot leave an existing dispatch's state inconsistent.
